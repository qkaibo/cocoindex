# CocoIndex 索引死锁排查报告

> **项目**: qcm4490 AOSP BSP 语义索引 (BGE-M3 + Qdrant + LMDB)
> **日期**: 2026-08-05 ~ 2026-08-06
> **状态**: 根因已实证, python 层修复已落地, 索引重启运行中

---

## 一、问题现象

`cocoindex update qcm4490:qcm4490_bsp` 在跑到 ~45,000 个文件时**反复死锁冻结**:

- 日志最后一行 `Elapsed: 1317.3s` 后不再更新
- 进程 CPU 时间不再增长(冻结)
- Python 层全部挂起:
  - MainThread 在 `asyncio select()` 空转(无 task 运行)
  - Thread-2 producer 卡在 `async_adapters.py:67 queue.put`(队列满,引擎不消费)
  - 60+ ThreadPoolExecutor 全 idle
- Qdrant / 磁盘 / 内存均正常(排除 OOM、磁盘满、Qdrant 挂死)

**历次死锁卡点**: 20,248 / 25,728 / 45,195

## 二、调查过程

### 2.1 第一阶段: 怀疑 tokio coop 预算 (已推翻)

**假设**: `storage.rs try_run_once` 持 LMDB 写锁跨 await, tokio coop 预算(128 poll/task)耗尽时强制让出, 而 `run_batch` 用 `tokio::select!` 嵌套驱动, coop 让出不触发 waker → 持锁任务永久挂起 → 写锁悬空。

**证伪**: 
- 并发从 128 降到 64 照样死锁
- **批=1 也死锁** —— 如果 coop 是根因,所有大文件都该死,但实际 95% 文件正常

**结论**: coop 理论不成立。批大小不是决定因素。

### 2.2 第二阶段: 实证定位 (gdb/py-spy 取证)

对冻结进程 1923351 做完整取证:

```
lock.mdb @0x40 写锁 = 0x801d5940
  contended=1(有人等锁), 持有者 TID = 1923392

Thread 103 (TID 1923392): tokio worker 空闲 park 循环
  worker::run → park → park_condvar → futex_wait
  【它根本没在执行任何代码!在睡觉!】

Thread 116 (TID 1923378): 卡在 storage.rs:181
  try_run_once → write_txn() → mdb_txn_begin → futex_wait
  【它想拿写锁,拿不到】
```

**关键发现**: 写锁被一个**僵尸任务**持有 —— wtxn 活在这个任务堆上的栈帧里, 任务挂起后 tokio 把它从 worker 上摘走, 线程去 park 睡觉, 但锁永远不释放。

### 2.3 触发诱因: 日志实锤

死锁前 3 分钟, 日志出现:

```
2026-08-05 23:40:43,025 ERROR cocoindex._internal.component_ctx: component build failed:
Traceback: httpcore.ReadTimeout: timed out
  → httpx.ReadTimeout: timed out
  → qdrant_client.http.exceptions.ResponseHandlingException: timed out
```

`1 ⚠️ errors` 从 39,528 一路带到 45,195 冻结 —— 失败组件一直挂着没被处理掉。

## 三、根因链条 (实证)

```
qdrant upsert 超时 (httpx 默认 5s 超时, 撞上 optimizer 合并 segment / swap 压力)
  ↓
组件 build 失败, 标记 exception
  ↓
引擎进入 cleanup_pending_token 无限重试 (execution.rs L1715-1735)
  每次重试调 clear_stage_marker → run_txn → 拿 LMDB 写锁
  ↓
但 LMDB 写锁已被【僵尸任务】持有 (wtxn 在挂起任务堆栈帧, 永不释放)
  ↓
清理永远失败 → 无限重试 → 引擎写路径全堵
  ↓
Python producer 队列满 → MainThread select() 空转 → 全进程冻结
```

### 为什么不是所有 upsert 都超时?

| 场景 | 结果 |
|---|---|
| 正常时刻: optimizer 空闲 | upsert 几十毫秒完成, 不超时 (99.9%) |
| 撞车时刻: optimizer 重写大 segment + swap 抖动 | 写入排队 > 5s → ReadTimeout (偶发) |

整个日志 7,500+ 行, `timed out` 只有 1 次。**这是偶发碰撞, 不是每次都超时。**

### 为什么不是所有文件都死锁?

触发条件是"组件失败"(qdrant 超时)这个**偶发事件**, 不是文件大小。95% 文件 upsert 正常, 走正常提交路径, 永远不会进死锁分支。

## 五、修复方案 (已落地, 纯 python)

### 5.1 改动内容

**① `pipeline.py` L296 (lifespan) + L732 (query)**:
```python
client = qdrant.create_client(QDRANT_URL, prefer_grpc=False, timeout=30)
```

**② `_target.py` `_apply_actions` upsert 加重试 (最多 3 次)**:
```python
_attempt = 0
while True:
    try:
        await asyncio.to_thread(self._client.upsert,
                                collection_name=self._collection_name,
                                points=_batch)
        break
    except Exception as _exc:
        _attempt += 1
        if _attempt >= 3:
            raise
        await asyncio.sleep(1.0 * _attempt)
```

### 5.2 修复逻辑

- timeout 5s → 30s: 撞 optimizer 高峰时等过去, 不误报失败
- upsert 3 次重试: 偶发抖动自动恢复, 组件不会进入失败 → 不触发清理路径 → 不死锁

### 5.3 为什么不动引擎

- 引擎 `storage.rs` 持锁跨 await + 僵尸任务 wtxn 泄漏是 Rust 层 bug
- 上游 cocoindex-io/cocoindex 同样存在, 无人报告
- 用户明令引擎源码不可改
